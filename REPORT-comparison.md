# UCMS — Requirements Audit Report

**Project:** UCMS  
**Path reviewed:** server/ (controllers, models, routes, middleware)  
**Date:** 2026-05-12

---

## Summary

This audit compares the current implementation against the requested workflow:

- Super Admin: top-level oversight of departmental admins and system activity.
- Departmental Admins: review complaints for their department; approve (forward to staff) or decline.
- Departmental Staff: work on approved complaints; mark them as Resolved and attach/upload a picture as proof.

Findings focus on implemented functionality, missing features, logical gaps, and suggested actions.

---

## Completed Features

- Complaint lifecycle basics:
  - Submission: `createComplaint` in `server/controllers/complaint.controller.js` supports creating complaints, optional file attachment, autos-creating departments, timeline entry `submitted`, and notifying admins.
  - Update/Delete by owner while pending: `updateComplaint`, `deleteComplaint` enforce pending-only edits and owner-only auth.
- Admin actions:
  - Approve: `approveComplaint` (sets `status = "approved"`, timeline entry, notification).
  - Reject: `rejectComplaint` (sets `status = "rejected"`, stores `rejectionReason`, timeline entry, notification).
  - Assign: `assignComplaint` (assigns a `Staff` user, sets `assignedTo`, `assignedBy`, `assignedAt`, timeline, notifications).
  - Analytics and dashboards for admin: `getAnalytics`, `getDashboard`.
- Staff actions:
  - View assigned complaints: `getAssignedComplaints` and `getAssignedComplaintDetail`.
  - Start work: `startWork` (sets `status = "in_progress"`, timeline entry, notifies submitter).
  - Complete work: `completeComplaint` (sets `status = "completed"`, `resolvedAt`, timeline entry, notifies submitter).
  - Upload proof image: `uploadProof` accepts a file via `uploadSingle` middleware, uploads to Cloudinary using `uploadBufferToCloudinary`, stores proof in `complaint.proof` and adds timeline entry and notification.
- File upload pipeline:
  - Memory multer middleware with file-type and size restrictions (`server/middleware/upload.middleware.js`).
  - Cloudinary upload helper `uploadBufferToCloudinary`.
- Data modeling:
  - Complaint model includes `attachments`, `proof`, `timeline`, `status` enum (`pending`, `approved`, `in_progress`, `completed`, `rejected`), and autogenerated `complaintId`.

## Missing Features & Workflow Gaps

1. **Super Admin role and oversight**
   - No `Super Admin` role exists in `server/models/User.model.js` (roles: `User`, `Admin`, `Staff`).
   - No API endpoints, middleware, or UI hooks for a Super Admin to oversee Admins or global activity.

2. **Departmental scoping for Admins**
   - Admin endpoints (`server/routes/admin.routes.js` use `requireRole("Admin")`) allow any `Admin` to:
     - View all complaints (`getAllComplaints`).
     - Approve/reject/assign any complaint regardless of department.
   - There is no check that an Admin belongs to the same `department` as the complaint before approving/assigning/rejecting.
   - `getPendingQueue` returns all pending complaints, not filtered by department.

3. **Enforcement of proof upload before marking resolved**
   - Staff can call `completeComplaint` which sets `status = "completed"` without requiring `proof`.
   - The required workflow states staff must attach/upload a picture as proof when marking resolved—this is not enforced.

4. **Role enum and status naming**
   - Requirement uses term "Resolved" but DB uses `"completed"`; inconsistent naming can cause confusion.

5. **Admin-level operations and department management**
   - No endpoint to create new Admin users or promote/demote users; only staff creation exists (`createStaff`).
   - No audit log or dedicated system activity stream for Super Admin monitoring aside from complaint timeline entries.

6. **Assignment validation gaps**
   - `assignComplaint` does not verify the `staff.department` matches `complaint.department`. Staff from other departments can be assigned.

7. **Authorization nuance in complaint access**
   - `getComplaintById` allows Admins to view all complaints; if departmental admins are intended to only see their department's complaints, additional checks are needed.

8. **Notifications and socket rooms**
   - Notifications are created for Admins by `createComplaint`, but socket usage emits to `"admin-room"` and general `io.emit` — no departmental room separation is implemented.

## Code Issues / Bugs / Improvements

1. **Missing role in enum**
   - `User.model.js` role enum: `enum: ["User", "Admin", "Staff"]` — must add `SuperAdmin` (or `Super`) if the requirement is to have a top-level role.

2. **No department check in admin controller**
   - `server/controllers/admin.controller.js` functions `approveComplaint`, `rejectComplaint`, `assignComplaint`, `getPendingQueue`, `getAllComplaints` do not verify admin's department. This is a security/logic bug for departmental admin model.

3. **Proof-not-required before completion**
   - `completeComplaint` in `server/controllers/staff.controller.js` sets `status = "completed"` without checking `complaint.proof`. A race/consistency/contract issue.

4. **Allowing cross-department assignment**
   - `assignComplaint` does not check `staff.department === complaint.department`.

5. **Missing admin creation or promotion flows**
   - No API to create Admin users or elevate an Admin to Super Admin, so role management is incomplete.

6. **Inconsistent status naming**
   - Use consistent status strings across codebase and frontend. Either support aliasing or standardize on `"resolved"` vs `"completed"`.

7. **Notification scoping**
   - Emitting events to broad channels (`io.emit`) and `"admin-room"` without department-specific sockets means departmental admins get noise from other departments.

8. **Potential edge cases / error handling**
   - Cloudinary upload could fail — controllers rely on `asyncHandler` but certain error messages may leak internal errors. Consider uniform error wrapping and retry/backoff if needed.

9. **Tests and validations missing**
   - No unit/integration tests found for enforcing departmental scoping, assignment rules, or proof-before-complete.

## Action Plan (concise implementation suggestions)

Priority order: (1) security/auth correctness, (2) workflow enforcement, (3) Super Admin and monitoring features.

- **Add Super Admin role**
  - Update `server/models/User.model.js` enum to include `"SuperAdmin"`.
  - Add `requireRole("SuperAdmin")` protected endpoints for global oversight (e.g., list all admins, activity logs).
  - Create endpoints: `GET /super/admins`, `GET /super/analytics`, `GET /super/activity`.

- **Enforce department scoping for Admins**
  - Store an `admin.department` for Admin users if required.
  - Add middleware to ensure Admins only affect complaints in their department (unless `SuperAdmin`).
  - Modify `admin.controller.js` to filter/validate by `req.user.department`.

- **Enforce proof upload before marking completed/resolved**
  - Recommended: Require `complaint.proof.length > 0` before `completeComplaint` marks completed.
  - Alternative: Provide an atomic `resolveWithProof` endpoint that accepts file + description and marks completed in one request.

- **Validate staff-department alignment on assign**
  - In `assignComplaint`, verify `staff.department` matches `complaint.department`.

- **Add Admin creation / promotion endpoints**
  - Provide secure endpoints for Super Admin to create Admins / promote users and add timeline entries for promotions.

- **Improve socket notification scoping**
  - Use department-specific rooms (e.g., `department_<deptId>`) and emit to them.

- **Standardize status naming**
  - Choose canonical status (`resolved` vs `completed`) and update code or add a mapping layer.

- **Tests & validation**
  - Add unit/integration tests for admin scoping, staff resolve-proof rules, and assignment validation.
